# backend

Модульный монолит проекта «Т-Инвестиции: тренажёр и лаборатория стратегий» на Java 25 и Spring Boot 4. Принимает команды фронтенда по REST и отдаёт события по SSE, хранит данные приложения в PostgreSQL, читает каталог бумаг из ClickHouse и запускает симуляции в C++ Simulation Worker по gRPC.

Общие знания — в репозитории `documentation` (локально `../documentation/`, на GitHub: https://github.com/tinkoff-trade-strategies-checking/documentation). Карта документов — `README.md` там; читай только то, что нужно для задачи. Процесс работы и указатели на остальные репозитории — в `home` (`../home/`).

Если документация репозитория противоречит существующему коду, следуй соглашениям кода и укажи расхождения в финальном ответе. Исключение — инварианты из `documentation/invariants.md`: их нарушение в коде считается багом.

## Стек и связи
- Java 25 (Gradle toolchain с автоскачиванием через Foojay), Gradle (Kotlin DSL), версии в `gradle/libs.versions.toml`.
- Spring Boot 4 + Spring Modulith 2 (корневой пакет `ru.tinvest.trainer`).
- PostgreSQL + Flyway (по схеме на модуль с таблицами).
- Качество: Spotless + `palantir-java-format`, статический анализ ErrorProne (ошибки роняют сборку), JUnit + Testcontainers.
- Внешние связи: REST/SSE по `api/openapi.yaml` (`backend#8`), gRPC к C++ Simulation Worker по копии `core/proto/` в `proto/` (`backend#9`), локальное окружение `deploy/` (`backend#10`).

## Как работать над задачей
Полностью — `home/workflow.md`. Коротко:
1. Работа идёт по issue с доски https://github.com/orgs/tinkoff-trade-strategies-checking/projects/2. Перед стартом прочитай issue вместе с комментариями.
2. Прочитай ФТ, INV и решения раздела «Архитектура» в `documentation/decisions.md`. Отход от принятого решения — только явно, PR в `decisions.md` с причиной.
3. Ветка `<тип>/<номер-issue>` в worktree (из `home`: `sh scripts/worktree.sh start backend <тип> <N>`), изменения вместе с тестами, PR с `Closes #N`.
4. Изменение сделало документы неверными — обнови их в том же PR.

## Критично
- **Границы модулей.** Зависимости между модулями проверяет `ModularityTest` (`ApplicationModules.verify()`). Межмодульное взаимодействие — только через публичный API и события.
- **INV-5 (неизменяемость).** Опубликованная версия стратегии (`workshop.strategy_version`) и снапшот (`marketdata.snapshot`) не меняются: `UPDATE`/`DELETE` запрещены триггерами в БД (миграции V2, V3); прогон (`simulation.run`) хранит ID версий без внешних ключей между схемами, существование проверяет код. Тесты: `StrategyVersionImmutabilityTest`, `SnapshotImmutabilityTest`, `RunRepeatTest` (`src/test/java/.../{workshop,marketdata,simulation}`), общая база — `PostgresIntegrationTest`.
- **INV-6 (деньги).** Денежные суммы и цены — только `BigDecimal` (масштаб и `RoundingMode` — по `decisions.md`, «Деньги и округление»), без `float`/`double`.
- **INV-7 (слепой режим).** Маскирование названий, тикеров, реальных дат и рублёвых сумм — в одном месте, с контрактным тестом; данные слепого режима не должны попадать в ответы об ошибках и логи.
- **INV-8 (восстановление сессии).** Ручная сессия хранится как журнал команд; состояние восстанавливается проигрыванием журнала.

## Стандарты
Общие стандарты — `home/standards.md`. Специфика Java/Spring для `backend`:
- **Формат и статический анализ.** `palantir-java-format` через Spotless (`./gradlew spotlessApply` / `./gradlew spotlessCheck`) и ErrorProne при компиляции — проверяются в CI, падение = ошибка.
- **Ошибки API.** Формат `ProblemDetail` (RFC 9457, `application/problem+json`), общий обработчик `ApiExceptionHandler` в модуле `api`. Ошибка входа — `InvalidRequestException` (`400`), нет ресурса — `NotFoundException` (`404`), недоступная зависимость — `DependencyUnavailableException` или ошибка доступа к БД (`503`); `IllegalArgumentException` и прочие JDK-исключения — `500`, их текст клиенту не уходит; на `500` клиенту не отдаются стек, внутренние сообщения, секреты и данные слепого режима.
- **Деньги (INV-6).** Только `BigDecimal`, масштаб и `RoundingMode` — по `documentation/decisions.md`, «Деньги и округление» (INV-6). Никаких `double`/`float` для цен, сумм и комиссий.
- **DTO и сущности.** DTO API (Java `record`) отделены от сущностей и таблиц БД; сущности БД не отдаются напрямую из контроллеров.
- **Слепой режим (INV-7).** Единая точка маскирования для ответов слепой сессии; все изменения покрываются контрактным тестом.
- **Зависимости и генерация.** Новые зависимости — с версией в `gradle/libs.versions.toml` и записью в `documentation/decisions.md` («Архитектура»). Сгенерированный код (gRPC-стабы и т. п.) не коммитится.
- **Язык.** Идентификаторы, API, таблицы и колонки — на английском; комментарии, документация и сообщения коммитов — на русском.

## Структура
Корневой пакет: `ru.tinvest.trainer` (`TrainerApplication`). Модули верхнего уровня (`documentation/architecture.md`, «Модули бэкенда»):
- `api` — общие правила HTTP API, безопасность, `ApiExceptionHandler` (RFC 9457 `ProblemDetail`) и `GET /api/health`.
- `identity` — учётные записи и вход пользователя (схема PostgreSQL `identity`): `/api/v1/auth/login`, `/auth/logout`, `GET /me`. Публичный API для других модулей — `identity.CurrentUser` (`requireId()` / `findId()`: UUID вошедшего пользователя); пароли bcrypt (до 72 байт UTF-8), роль одна — `USER`. Безопасность — `api.SecurityConfiguration`: cookie `SESSION` (HttpOnly, Secure, SameSite=Lax; сессии в памяти Tomcat), CSRF `XSRF-TOKEN` / `X-XSRF-TOKEN` (cookie выдаётся любым запросом, в том числе `GET /me` с 401), всё под `/api/v1/**` кроме входа требует входа (401 ProblemDetail), CSRF — 403; `/api/health` и `/actuator/health` открыты. Ограничитель попыток входа (`LoginRateLimiter`): `tryAcquire` атомарно проверяет и сразу учитывает попытку (до bcrypt); счётчики за `window` = 5m по паре (почта, IP) (`identity.login-limit.max-failures-per-pair` = 5), по IP (`max-failures-per-ip` = 20) и общий по почте со всех IP (`max-failures-per-email` = 50); общий порог по почте не действует на «известную» пару — с успешным входом за `known-pair-ttl` = 30d (в памяти, не больше `max-known-pairs` = 10000 пар); лимит самой пары действует всегда. Сверх лимита — 429 ProblemDetail с `Retry-After` (секунды вверх, не меньше 1); 429 в счётчики не пишется, сбой БД (503) попытку возвращает. Успешный вход сбрасывает счётчик пары и снимает свою попытку, чужие неудачи по почте не стирает. Память счётчиков: около 20 КБ на IP атакующего, потолка числа ключей нет — для одного экземпляра допустимо. Остаточный риск: счётчики и список известных пар в памяти одного экземпляра, не общие между экземплярами и теряются при рестарте; после рестарта, а также для нового IP владельца (его пары ещё нет в списке) перебор с ≥10 адресов за окно блокирует почту до конца окна. Почта в запросе (после нормализации) и в БД — не длиннее 254 символов (400; CHECK в V11). IP клиента — из `X-Forwarded-For` Caddy (`server.forward-headers-strategy: native`); `server.tomcat.remoteip.internal-proxies` сужен до закреплённой подсети `internal` (`172.28.0.0/24` в `deploy/docker-compose.yml`, проверяет `DeployExposureTest`), при локальном `bootRun` без Caddy `X-Forwarded-For` не доверяется. Сбой БД при входе — 503, не 401. Новый защищённый контроллер ничего настраивать не должен; в тестах MockMvc сессия и CSRF — как в `IdentityApiTest`.
- `config` — общие настройки приложения.
- `worker` — связь с Simulation Worker по gRPC, передача заданий и результатов. Публичный интерфейс — `SimulationWorkerClient` (`ping()`, `classifyPeriods(...)` — окна периодов и пороги из `ClassifyPeriods` core, `replaySession(...)` — проигрывание журнала до курсора, `estimateOrder(...)` — оценка заявки и перевод слепых цен, `checkStrategy(...)` — статическая проверка и линтер DSL, `runStrategy(...)` — потоковый прогон алгоритма, `analyzeDivergences(...)` — разбор расхождений с алгоритмами); типы обмена — Java-записи `WorkerTypes` (деньги — `BigDecimal` из `Decimal`, перевод — `WorkerMapper`); реализация на `ManagedChannel`, адрес `worker.address` (env `WORKER_ADDRESS`, по умолчанию `localhost:50051`), дедлайн унарного вызова `worker.deadline` (env `WORKER_DEADLINE`, по умолчанию `5s`), дедлайн прогона `worker.run-deadline` (env `WORKER_RUN_DEADLINE`, по умолчанию `10m`, НФТ-7); `UNAVAILABLE` и `DEADLINE_EXCEEDED` → `DependencyUnavailableException` (503).
- `marketdata` — каталог бумаг и доступной истории; подбор отрезка выбранной категории периода (схема `marketdata`). Импортёр архива ISS — пакет `marketdata.importer` (профиль `import`, раздел «Импорт архива ISS»). Бенчмарк IMOEX пишется и в `securities` (лот 1, шаг 0,01, сектор пустой: так ждёт core), но в пул бумаг сессии не входит: `ClickHouseArchive.secids` и `ArchiveCatalog.securities` его исключают.
  Подбор запуска (backend#23) — `LaunchPlanner.plan(LaunchRequest[, snapshotId, seed])` → `LaunchPlan` или `LaunchRejection` (причины как `LaunchRejectReason` контракта); раздел «Подбор запуска».
- `workshop` — черновики стратегий, проверка DSL через воркера (`CheckStrategy`), публикация неизменяемых версий (V2, V16), форки (UC-20) и скрытие из каталога (UC-21) (схема `workshop`). Публичный API: `StrategyCatalog`, `StrategyVersions`.
- `sessions` — ручная торговля: журнал команд, виртуальное время, плеер, слепой режим, завершение и воспроизведение (схема `sessions`). Название бумаги из каталога (`securities.name`) сохраняется в `sessions.session_paper.name` при запуске (V14) и отдаётся в раскрытом виде (снимок раскрытой сессии, воспроизведение завершённой слепой, отчёт), нет названия — тикер; идущая слепая названий не видит (INV-7). Сделано: запуск сессии (`POST /sessions`, раздел «Запуск сессии»), хранилище `Sessions`, `BlindMasking`, арена — снимок, заявки, оценка (раздел «Арена»), плеер, SSE и завершение (раздел «Плеер и поток событий»). Воспроизведение завершённой сессии — `GET /sessions/{id}/replay?step=N[&fromStep=M]` (`Replay`, `ReplayViews`): журнал с шагами не позже `step` проигрывается воркером, шаг дальше итогового (`current_step` завершённой сессии) ограничивается им; идущая сессия — `NOT_FINISHED` (`PublicViews`), чужая — `NOT_FOUND` со статусом 200. Публичный вход для `analysis` — `SessionArchive` (`lookup`, `history`) и `SessionLookup`.
- `simulation` — очередь вычислительных заданий (`RunQueue`, `RunExecutor`, настройки `lab.simulation.*`: лимиты на пользователя `max-running-per-user` = 3 одновременных `running` и `max-queued-per-user` = 20 в `queued` → `429 TOO_MANY_REQUESTS` под `pg_advisory_xact_lock`), прогоны алгоритмов и повтор прогона (схема `simulation`, V4, V17): `POST /api/v1/runs` (повторная проверка `checkStrategy` → `422 STRATEGY_INVALID`, планирование `LaunchPlanner` под `@ConditionalOnWebApplication`), `GET /api/v1/runs/{runId}` (INV-7: без периода/бумаг пока слепой прогон активен), `POST /api/v1/runs/{runId}/repeat` (UC-18, INV-4: сверка `digest` и `finalEquity` → `repeatMatch`), `GET /api/v1/runs/{runId}/events` (SSE с `Last-Event-ID`). Публичный вход для `analysis` — `RunArchive` (`lookup`, `findOwned`, `findResult`, `history`) и `RunLookup`.
- `analysis` — отчёты, история, сравнение результатов, разбор расхождений и выгрузка CSV/XLSX (схема `analysis`). Сделано (backend#26, backend#11, backend#54, backend#61): отчёт сессии строится в фоне по событию `sessions.SessionFinished` (`ReportBuilder`, после фиксации; `buildAndStore` — ядро проигрывает журнал с `include_report` и при наличии `algoVersionId` V18 вызывает `AnalyzeDivergences` для ФТ-18…20) и сохраняется в `analysis.session_report` (V10, неизменяем; V13 — версия формата `StoredReports.FORMAT_VERSION = 3` в ключе: отчёт другой версии при чтении считается отсутствующим и собирается заново отдельной строкой; менять версию при изменении формы или смысла полей отчёта, миграция очистки при этом не нужна); `GET /sessions/{id}/report` читает сохранённый (`BUILDING`, пока его нет, и запрос подстраховывает сборку); `POST /sessions/{id}/report/compare` (`SessionCompareController`, `SessionCompareService`, `SessionCompareViews`) сравнивает завершённую сессию постфактум с 1–5 алгоритмами из каталога Мастерской через `AnalyzeDivergences` и отдаёт разбор по каждому алгоритму и сводный `consensus` без изменения сессии и сохранённого отчёта (`INV-5`). Отчёт прогона алгоритма (`RunReportController`) читается из `simulation.run_result`: `GET /api/v1/runs/{id}/report` (`READY`/`BUILDING`/`NOT_FINISHED`/`NOT_FOUND`) и `GET /api/v1/runs/{id}/report/export?format=xlsx|csv` (`run-<id>.xlsx`/`run-<id>.zip`, `ReportSheets.ofAlgoRun`). `GET /history` (`HistoryController`) объединяет сессии (`SessionArchive`) и прогоны алгоритмов (`RunArchive`, `kind=algo_run`, статусы `HistoryStatus` включая `invalid`/`failed`); незавершённая слепая запись — `BLIND_UNFINISHED` без раскрытых полей (INV-7).
  Выгрузка (backend#12, ФТ-17): `GET /sessions/{id}/report/export?format=xlsx|csv` (`ReportExportController`) строит файл из сохранённого отчёта (`ReportSheets` — листы и формат ячеек, `ReportFiles` — XLSX на `org.dhatim:fastexcel` и CSV в ZIP), воркер не вызывается; имя `report-<id>.xlsx` / `report-<id>.zip`. Чужая и несуществующая сессия — 404, идущая (в том числе слепая) и ещё не построенный отчёт — 409 `ProblemDetail` без данных сессии, неизвестный `format` — 400. CSV — строки отчёта (запятая вместо точки, метрики до 6 знаков), в XLSX деньги и метрики — числовые ячейки из `BigDecimal` без `double` (форматы `#,##0.00`, `0.000000`, `0.00`); время МСК. Лист «Заявки» — команды журнала (`SessionArchive.commandLog`: подача, отмена, замена и приём или отказ с причиной); итог заявки (исполнена, снята) в журнале не хранится — он у ядра, исполнения в выгрузку не входят.

Миграции Flyway — в `src/main/resources/db/migration/` (`V1__baseline.sql` создаёт схемы модулей). Нумерация: `V<N>__<что>.sql`, по возрастанию в одном каталоге; таблицы модуля — только в его схеме. Конфигурация — `src/main/resources/application.yml` (БД из `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`, без значений по умолчанию) и профиль `application-local.yml` (значения для локального запуска).

## Создание пользователя
Регистрации нет, учётные записи заводит команда профилем `create-user` (без веб-сервера, нужен PostgreSQL; для локальной БД добавьте `local`). Пароль лучше передавать переменной `USER_PASSWORD` (не виден в списке процессов), допустим `--user.password`:

```bash
USER_PASSWORD='...' ./gradlew bootRun --args='--spring.profiles.active=create-user,local --user.email=trader@example.com'
```

Почта хранится в нижнем регистре и уникальна без учёта регистра; пароль длиннее 72 байт UTF-8 отклоняется. Сброс пароля — команда вручную (решение «Учётные записи»).

## Импорт архива ISS
Импортёр (UC-26, `backend#7`) грузит MOEX ISS и ставки RUONIA ЦБ РФ в ClickHouse как неизменяемый снапшот и регистрирует его в `marketdata.snapshot` (`Snapshots.register`). Запускается тем же приложением под профилем `import` (без веб-сервера), нужны PostgreSQL и ClickHouse:

```bash
./gradlew bootRun --args='--spring.profiles.active=import,local --import.from=2024-01-01 --import.to=2024-12-31 --import.tickers=SBER,GAZP'
```

- Без `--import.tickers` пул — состав индекса IMOEX на `--import.to` (ближайший торговый день не позже). `--import.label=<текст>` — новый снапшот на тех же параметрах.
- ClickHouse: `IMPORT_CLICKHOUSE_URL` (HTTP, например `http://localhost:8123`), `IMPORT_CLICKHOUSE_DATABASE`, `IMPORT_CLICKHOUSE_USER`, `IMPORT_CLICKHOUSE_PASSWORD` — без значений по умолчанию, не заданы — запуск падает. PostgreSQL — `SPRING_DATASOURCE_*` как в `application.yml`; для локального запуска добавьте профиль `local` (`import,local`). `--import.allow-gaps=true` принимает пробелы покрытия (ниже). ISS и повторы — `--import.iss.*` (`pause`, `max-retries`, `initial-backoff`, `max-backoff`, `empty-retries`, `base-url`), ЦБ — `--import.cbr.url`.
- Что грузится: минутные свечи пула с TQBR (`candles`, `interval_sec = 60`, `ts_open` — UTC из МСК = UTC+3, `available_at = ts_open + интервал`), дневной ряд IMOEX (`interval_sec = 86400`), `securities` (лот, шаг цены `MINSTEP`, сектор, `name` — `SHORTNAME` из ISS, нет — `SECNAME`; столбец сверх контракта `core`, он читает столбцы по именам; на старых таблицах импортёр делает `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, каталог читает и архив без этого столбца (названия пустые, схему веб-приложение не меняет); название идёт только в `GET /papers`, в слепой вид не попадает), `trading_calendar` (торговый день — день с дневной свечой IMOEX), `ruonia`, `corporate_actions` (сплиты и консолидации из `statistics/engines/stock/splits`, таблица сверх контракта `core`), затем `snapshots_ready`. Календарь и ставки берутся с запасом 14 дней до `--import.from`. Бумага не на TQBR, с шагом цены < 1e-6 ₽ (или больше шести знаков) или лотом < 1 пропускается с предупреждением. Цены и шаг цены разбираются без округления (больше шести знаков — ошибка, INV-6), оборот свечи (`value`, double с артефактами в ISS) округляется HALF_UP до 6 знаков. Сектор — по вхождению в отраслевые индексы MOEX на дату состава: несколько индексов — тот, где вес бумаги (`weight` из `analytics`) наибольший, равные веса — индекс с меньшим кодом (`ArchiveImporter.sectorIndex`); нет индексов — пустая строка (бумага не попадёт в слепой пул `LaunchPlanner`, неслепым сессиям доступна); оба случая (индексов не один) с предупреждением в логе. Хэш снапшота (`marketdata.snapshot.data_hash`, `Snapshot.dataHash`, строка `хэш: sha256:…` в `description`) — SHA-256 над строками `таблица(столбцы)|число строк|сумма 128-битных sipHash128 строк` по `securities`, `candles`, `trading_calendar`, `ruonia`, `corporate_actions` (без `snapshot_id`): не зависит от порядка вставки, докачки и `label`, меняется при любом изменении данных; считается после `snapshots_ready`.
- Идемпотентность: `snapshot_id` = UUID по имени от параметров (`Params.snapshotId`). Зарегистрированный снапшот не меняется (INV-5): повторный запуск с теми же параметрами ничего не делает. Оборванный запуск докачивается: каждая таблица и каждый кусок (бумага × месяц) вставляются одним атомарным `INSERT`, «в таблице есть строки» значит «загружено». Снапшот виден `core` только после `snapshots_ready`; готовый в ClickHouse, но не зарегистрированный в PostgreSQL только регистрируется.
- RUONIA (ЦБ РФ, `cbr.ru/hd_base/ruonia/dynamics`): фильтр по дате ставки (`Posted=True` — только признак формы), ставка хранится по своей дате без `available_at`: `core` в день d берёт `RUONIA_{d-1}` и сам переносит последнюю ставку на выходные (`matchRuoniaRates`), заглядывания вперёд нет. Ставка за дату D выходит в D+1, поэтому за последние 1–2 рабочих дня её может не быть; на праздники ЦБ ставку не публикует.
- Целостность: пустая страница при известном `TOTAL` (аналитика, состав индексов) — ошибка, а не конец данных. У свечей курсора нет, поэтому покрытие проверяется ДО вставки куска «бумага × месяц»: ожидаемые дни — торговые дни календаря IMOEX внутри куска и периода торгов бумаги на TQBR (`listed_from`…`listed_till` из ISS; нет данных — весь кусок); в каждый ожидаемый день должны быть свечи, и последняя — не раньше начала последней 10-минутной свечи IMOEX за этот день минус `--import.end-of-day-tolerance` (по умолчанию `30m`; обрыв посреди дня; на 03.2024 IMOEX — 18:50, SBER — 23:49 МСК). Не проверяется: пропуск минут внутри дня и день, где бумага торговалась меньше индекса в пределах допуска; день без внутридневных свечей IMOEX проверяется только на наличие свечей. Проблема — отчёт в лог и `ImportException`, кусок не вставляется (докачка его перекачает). `--import.allow-gaps=true` принимает проблемы с предупреждением и принятые проблемы остаются в снапшоте. В `description` всегда пишутся пробелы, найденные по ClickHouse (`пробелы: <бумага>: N дн. [даты]`, больше пяти дат — первые три и последние две через «…», независимо от флага последнего запуска; оборванные дни — только из текущего запуска), и `allow-gaps: включён`, если флаг задан.
- Календарь IMOEX проверяется до вставки годового куска. Пустой ответ — всегда `ImportException` (иначе пустой календарь попал бы в неизменяемый снапшот). Подозрительно редкий ряд — месяц, целиком внутри куска, с долей торговых дней меньше 50 % будней, или первый/последний день дальше 10 дней от границы куска — бывает и на настоящих событиях (остановка торгов 28.02–23.03.2022), поэтому без `--import.allow-gaps=true` это `ImportException` с объяснением, с флагом — WARN и запись `календарь: 2022-03 6 из 23 будних` в `description` (по данным ClickHouse, как пробелы). Неполные месяцы на краях и доля за весь кусок не проверяются: на коротком периоде с январём (~74 % будней) они ложно малы. Сверить с ISS-календарём нельзя: `trading_calendar` выводится из этого же ряда.
- Параллельный запуск с теми же параметрами невозможен: advisory lock PostgreSQL по ключу снапшота. ISS и ЦБ получают `User-Agent: trainer-importer/<версия>`.
- ISS: пауза между запросами, ошибка (сеть, не 200, не JSON) — повтор с экспоненциальной задержкой, пустая страница — до `empty-retries` повторов, затем конец данных; следующая страница нужна, пока страница полная (500 для свечей) или не набран `TOTAL` из `<блок>.cursor`.
- Тесты `marketdata/importer`: поддельный ISS на JDK `HttpServer` с образцами из `src/test/resources/iss`, настоящие ClickHouse (Testcontainers) и PostgreSQL, сети нет.


### Полная загрузка пула (~3 суток)
Версия схемы импорта — 2 (в идентификаторе снапшота): недогруженная загрузка по версии 1 не докачивается, импорт отказывает и называет её id; `--import.drop-legacy=true` удаляет строки этого снапшота (строго по id, из всех таблиц архива) и грузит заново; каталог на архиве без столбца `securities.name` отдаёт пустые названия.
Загрузка идемпотентна по кускам «бумага × месяц»: после остановки (Ctrl+C, обрыв сети, перезагрузка) повторный запуск с **теми же** `--import.from/to/tickers/label` докачивает недостающее, загруженное не качает заново. Поэтому запускать можно по частям и в фоне: `nohup ./gradlew bootRun --args='--spring.profiles.active=import,local --import.from=… --import.to=…' > import.log 2>&1 &`, следить по `import.log` (строки «`<бумага> <месяц>: N свечей`»), при падении — запустить ту же команду снова. Другие параметры или `label` — другой снапшот с нуля. Снапшот регистрируется в PostgreSQL только после полной загрузки.
## Подбор запуска
`marketdata.LaunchPlanner` подбирает период и бумаги для ручной сессии, ничего не пишет. Бин обязателен: нужен `marketdata.clickhouse.url` (`MARKETDATA_CLICKHOUSE_URL`, а также `_DATABASE`, `_USER`, `_PASSWORD`, `_TIMEOUT`; в `deploy/` заданы), без него (пустая строка — тоже) веб-приложение не стартует. Без веб-сервера (профили `import`, `create-user`) подбор и всё, что его использует (`MarketdataConfiguration`, `LaunchService`, контроллеры), не создаётся: условие `@ConditionalOnWebApplication` одно на всю цепочку, новые зависимости от `LaunchPlanner` ставьте под него же (тест `FullApplicationProfilesTest` поднимает всё приложение в `import`, `create-user` и обычном режиме); профиль `local` задаёт `http://localhost:8123`, база и пользователь `ttsc`. Каждый `@SpringBootTest` (в том числе с собственными `properties`) задаёт заглушку `marketdata.clickhouse.url=http://localhost:1`. Остальное — `marketdata.pool` (тикеры IMOEX; пусто — все бумаги снапшота), `marketdata.max-bars` (5000).

- Снапшот — последний готовый (есть в `snapshots_ready`) или заданный; заданный и не готовый — `NotFoundException`; нет готового — `DependencyUnavailableException` (503, в контракте нет подходящей причины отказа).
- Календарь, интервалы, бумаги, даты свечей и сплиты читаются из ClickHouse один раз на снапшот (`CachingArchiveCatalog`, снапшот неизменяем); на запрос — только `sessionSteps`. Кэш держит последние `marketdata.cache-snapshots` снапшотов (2); чтения без блокировки карты: одновременные запросы одного ключа ждут общий результат, провал (таймаут) не кэшируется, чтений из ClickHouse одновременно не больше `marketdata.max-concurrent-scans` (2). После старта кэш последнего готового снапшота прогревается в фоне (`marketdata.warm-up`, `LaunchPlanner.warmUp`). Первый скан `candleDays` читает свечи всего снапшота; таймаут `marketdata.clickhouse.timeout` (120 с) **не проверен на полном архиве**: замерить, когда архив будет загружен целиком.
- Торговый день — дата МСК календаря IMOEX, все сессии дня входят в него. Бумага покрывает окно, если свечи есть в каждый торговый день окна.
- Лимит `max-bars` — «на одну бумагу» = шаги общей шкалы сессии (она общая для всех бумаг): число разных начал свечей шага по объединению выбранных бумаг в окне, точно по архиву, ≤ 5000, граница включительно. Торговый день — дата календаря IMOEX: свечи бумаг вне календаря (торги в выходные) в шкалу не входят (`ArchiveCatalog.sessionSteps` берёт список торговых дней окна). `Timeframe.minCandlesPerDay` (только основная сессия) — лишь ранний отсев заведомо невозможных пар; тогда `barsCount` в отказе — нижняя граница.
- Капитал: от 10 000 до 100 000 000 ₽, до 2 знаков; пресеты 100 000 / 500 000 / 1 000 000 (по умолчанию) / 5 000 000 — `LaunchPlanner.CAPITAL_PRESETS`, `DEFAULT_CAPITAL` (решение владельца продукта, 19.11.2026).
- Прогрев: `LaunchPlanner.WARMUP_BARS` = 200 шагов до начала периода. Сплит или консолидация бумаги в окне прогрева (оценка в днях по `Timeframe.minCandlesPerDay` с запасом в день, не дальше первого дня календаря) отсекают отрезок так же, как внутри периода (`CORPORATE_ACTION_ON_PERIOD` / пропуск окна).
- Отказы: капитал вне диапазона (формат строки `Money` и `durationDays` из enum проверяет контроллер — 400), число бумаг не 1–5, дубли и посторонние `paperIds`, лишние поля не своего режима, нет `customStartDate`, шаг без данных в архиве — `INVALID_PARAMS` с именем поля; шагов больше предела — `TOO_MANY_BARS` с `barsCount`/`maxBars`; свой отрезок не той категории или не найден (core: `INVALID_ARGUMENT` на `start_date`, клиент воркера отдаёт пустой список), нет окна категории или бумаг с полным покрытием — `NO_MATCHING_PERIOD`; сплит или консолидация бумаги внутри окна — `CORPORATE_ACTION_ON_PERIOD` (для своей даты; при случайном выборе такие бумаги не берутся). Воркер без данных снапшота (`FAILED_PRECONDITION`, `NOT_FOUND`) и недоступный — 503.
- Шаг доступен, если в архиве есть свечи этого интервала или минутные (core агрегирует). `GET /launch/options` отдаёт для каждого доступного шага `maxDurationDaysByTimeframe`: `max-bars / наибольшее за день число шагов шкалы по всем бумагам снапшота` (консервативно; `LaunchPlanner.maxDurations`, один проход по свечам на источник, кэшируется и прогревается); экран выключает бóльшие длительности, пограничное решает `422 TOO_MANY_BARS`.
- Слепая сессия (`RANDOM`): окна категории перемешиваются по `seed`, берётся первое, где набралось N бумаг с сектором, с покрытием, без сплитов и с числом шагов в пределах лимита; бумаги — случайные N из них. Бумаг с сектором меньше `paperCount` — `INVALID_PARAMS` / `paperCount` (смена категории не поможет). Окно с превышением лимита пропускается, а не отказывает (иначе результат зависит от seed); после 50 таких проверок (компромисс: до 50 запросов `sessionSteps` на один `POST`, а дальше могли быть подходящие окна) или когда окон не осталось — `TOO_MANY_BARS` без `barsCount` (число шагов скрытого окна клиенту не раскрывается), только `maxBars`. Своя дата (`CUSTOM`): категория окна из `ClassifyPeriods(start_date)` должна совпасть с выбранной, бумаги — выбор пользователя, превышение лимита — отказ с `barsCount`.
- Идентификатор бумаги в API — `Papers.id(secid)`: UUID по имени от тикера, одинаков во всех снапшотах.
- INV-1/INV-7: даты окна, σ, MDD, пороги и тикеры — только для backend; `toString` у `LaunchPlan`, `PlannedPaper`, `PeriodWindow` их не печатает, клиенту до конца сессии отдаются категория, секторы, число свечей и капитал.

## Запуск сессии
`POST /api/v1/sessions` (`sessions.SessionsController`) → `LaunchService` → `LaunchPlanner.plan` → `Sessions.create`; `GET /launch/options` и `GET /papers` отдаёт `marketdata.LaunchCatalogController`. Отказ подбора — `422` `LaunchProblem` (`code`, `field`, `barsCount`, `maxBars`), неверная форма запроса (неизвестное значение перечисления, нет поля, капитал не число) — `400`, недоступный воркер или архив — `503`; сессия при отказе не создаётся.
- Схема `sessions` (миграция `V6`): `session` (владелец `user_id`, параметры запуска, план: `snapshot_id`, период, категория, σ, MDD, пороги, число свечей, капитал, `blind`, `status`), `session_paper` (бумага с `paper_index` — индекс в сессии, порядок случайный, не по тикеру), `command_journal` (INV-8; только дописывается, заполняют задачи про заявки). Триггеры БД: план и параметры сессии, бумаги не меняются, `status` меняется только из `running` в `completed`/`finished_early`/`bankrupt` (названия как `HistoryStatus` контракта), сессию нельзя удалить, журнал без `UPDATE`/`DELETE`, на трёх таблицах запрещён `TRUNCATE`. Вставка бумаг в уже созданную сессию БД не запрещает: бумаги пишет только `Sessions.create` в транзакции создания. Внешних ключей в чужие схемы нет, снапшот и пользователя проверяет код.
- Доступ по владельцу — только через `Sessions.requireOwned(id)`: чужая сессия неотличима от несуществующей (`404`). Последующие операции сессии берут сессию так же.
- Маскирование (INV-1, INV-7) — только `sessions.BlindMasking`: ответ запуска (`CreatedSession` — один `sessionId`, одинаково для слепой и неслепой) и тело `422` (константный `detail`, без дат, тикеров и метрик). Новые виды ответов сессии (снимок, события, заявки) строятся там же. `SessionRecord`, `PaperRecord`, `LaunchPlan` не печатают данные в `toString`. Тест `SessionLaunchApiTest` проверяет, что ответ слепого запуска не содержит тикеров, секторов, дат и рублей.
- Параметры экрана запуска, не заданные решениями: `defaultRegime` = `medium`, `defaultPaperCount` = 3, `name` бумаги в `/papers` = тикер (названий в архиве нет) — вопросы к владельцу продукта.

## Арена
`ArenaController` → `Arena` (пакет `sessions`): `GET /sessions/{id}` (снимок на курсоре), `POST /sessions/{id}/orders`, `DELETE|PUT /sessions/{id}/orders/{orderId}`, `POST /sessions/{id}/order-estimate`. Ответы строит `BlindMasking` (слепой вид — из `blind_view` воркера, раскрытый — `OpenViews`); чужая сессия — 404.
- **Состояние = проигрывание журнала (INV-8).** Воркер без состояния: на каждый запрос уходит `MarketSpec` сессии (`Arena.market`: бумаги по `paper_index`, ключ бумаги = тикер, издержки и прогрев берутся из строки сессии: при запуске `Sessions.create` фиксирует `Sessions.DEFAULT_COSTS` (значения по умолчанию из `decisions.md`) и `LaunchPlanner.WARMUP_BARS` = 200 шагов (миграция `V8`, с `V15` по умолчанию `200`, существующим сессиям — прежние значения); `benchmark` IMOEX), весь журнал и курсор `sessions.session.current_step` (миграция `V7`, не убывает). Чтение снимка и оценка ничего не пишут.
- **Журнал** (`ArenaJournal`, `command_journal`): команда в рублях JSON-ом (бумага — индексом сессии, не тикером), `step` — курсор на приёме, `seen_step`, `accepted`, `reject_reason`, `reject_field`. Подача: расчёт номера `seq` под блокировкой строки сессии (`Sessions.requireOwnedForUpdate`), `ReplaySession` по журналу с новой командой даёт итог (`command_results`), затем запись. Отказ воркера пишется с `accepted = false`; отказ до воркера (форма, `seenStep` больше курсора, сессия не `running` — `SESSION_NOT_ACTIVE`, слепая цена без `resolved_order`) в журнал не пишется и возвращается 200 с `accepted: false`.
- **Слепая заявка**: цены экрана уходят в `EstimateOrder` с `is_blind_price = true`, в журнал идёт `resolved_order` (каждая нога OCO — отдельной оценкой). Замена берёт бумагу, сторону и тип у заменяемой заявки (состояние воркера), в запросе — лоты, срок, цены; у OCO заменяется пара. Оценка OCO: суммы первой ноги (стоп), `canPlace` — по обеим.
- **Поля ядра → поля контракта**: уровень тейк-профита в ядре — `limit_price` (контракт — `takeProfitPrice`), `trailing_percent` — `trailingPct`; `invalid_field` переводится обратно (`Arena.clientField`).
- **Идентификаторы**: заявка наружу — UUID v7, в ядре `seq * 2 + нога`; соответствие `sessions.order_ref` создаётся при первом показе (`OrderRefs`). Исполнение — UUID v5 от (сессия, `fill`, заявка, шаг) (`DerivedIds`).
- **`Idempotency-Key`** (`Idempotency`, `sessions.idempotency_key`): область — сессия. Ключ занимается атомарно (первичный ключ) отдельной зафиксированной записью `in_progress` с токеном захвата; под блокировкой сессии внутри транзакции команды ключ перечитывается (`recheck`), ответ пишется в той же транзакции, что и журнал, и только владельцем токена (`complete`). Тот же ключ и тело — прежний ответ без записи в журнал, другое тело или операция — 422 `IDEMPOTENCY_KEY_REUSED`, первый запрос ещё идёт — 409 `IDEMPOTENCY_KEY_IN_PROGRESS`. Ошибка команды (воркер недоступен) освобождает ключ. Перехвата ключа по времени нет; `in_progress`, оставшийся после остановки процесса, снимается при следующем запуске (`dropAbandoned`; backend один — при нескольких экземплярах это нужно пересмотреть). Отпечаток тела — `OrderRequest.fingerprint`.
- **Деньги и издержки (решение владельца продукта, 19.11.2026).** Backend не складывает и не округляет: `cost` и `costPct` исполнения считает core (core#54), backend передаёт как есть; `ViewFormat.money` не округляет — лишний знак у суммы ядра это `ArithmeticException` (500), а не молчаливое округление.
- Производные величины core#54 (проценты и `invested/pnl/costs` портфеля, `valuePct`/`pnlPct` позиции, `amountPct`/`costPct`/`cost` исполнения, `changePct` бумаги = `period_pct`, номер дня `current_day`) backend отдаёт как есть, без `null`; `changePct` `null` только у бумаги без бара на курсоре. Идентификатор исполнения — UUID v5 от (сессия, `Fill.seq`). `playing`/`speed` снимка — состояние плеера (`sessions.player_state`).
- **Бумага без бара до курсора.** Раскрытая сессия показывает её с пустыми `candles` и `lastPrice: null`; заявку на неё ядро отклоняет (`INVALID_PARAMS`, поле `paperId`) до первого бара. В слепом виде такой бумаги нет целиком (`blind_view`).
- **Оценка OCO — по ногам.** `order-estimate` отдаёт `legs` (стоп и тейк-профит отдельно), суммы верхнего уровня — первой ноги, `canPlace`/`reason`/`field` — по всем ногам; пусто, если оценки нет (отказ до расчёта, сессия не `running`: суммы нулевые).
- **Известные ограничения.** Транзакция команды держит соединение пула и блокировку строки сессии на время 2–4 вызовов gRPC (дедлайн `worker.deadline` каждый); `GET /sessions/{id}` пишет `sessions.order_ref` (идемпотентно, `ON CONFLICT DO NOTHING`); снимок и оценка читают сессию и журнал без общей транзакции — когда плеер (backend#25) начнёт двигать курсор, читать в одной транзакции (`REPEATABLE READ`) или отбрасывать записи с `step` больше курсора; оценка для не `running` сессии отдаёт нулевые суммы и `referencePrice "0.00"` (контракт требует значение).
- Тесты: `ArenaApiTest` (PostgreSQL, MockMvc, воркер — `FakeWorker` без состояния: слепой перевод ×2, лимит лотов, рыночная заявка исполняется на следующем шаге, затвор для проверки гонок). INV-7: `blindMaskingHoldsForEveryAnswerOfGeneratedSessions` — на сгенерированных слепых сессиях каждый ответ (200, отказы, 400/404/409/422/503, повтор по ключу) содержит только поля слепых схем, ни тикера, ни реальной даты и времени, цены в слепой шкале; плюс `blindResponsesCarryNoTickersNamesDatesOrRubles`. INV-8: `stateIsRestoredFromTheJournalAlone`, `estimateNeverWritesTheJournal`, `repeatWhileTheFirstRequestIsRunningIs409ThenReturnsTheStoredAnswer`, `simultaneousIdenticalRequestsWriteOneJournalEntry`. INV-2: `rejectionsBeforeTheWorkerAreNotJournaled`, `sessionStoresWarmupAndCostsAtLaunchAndPassesThemToTheWorker` (`CHECK seen_step <= step`). `GrpcArenaMappingTest` — перевод proto ↔ записи.

## Плеер и поток событий
`PlayerController` → `Player` (пакет `sessions`): `POST /sessions/{id}/player` (play, pause, step, speed 1/5/10/100), `POST /sessions/{id}/finish`, `GET /sessions/{id}/events` (SSE).
- **Время ведёт сервер.** Курсор `current_step` двигают только такт часов (`Player.tick`) и `step`, оба под блокировкой строки сессии (поэтому арена видит согласованный курсор). Период такта — `1000/speed` мс, не чаще `lab.session.min-tick` (200 мс): ×1 — свеча в секунду, ×5 — свеча за такт 200 мс, ×10 — две, ×100 — двадцать. Часы и планировщик — интерфейс `PlayerTimer` (`SchedulerTimer` в приложении, `ManualTimer` с виртуальным временем в тестах: тесты не ждут реальных секунд). Такт не копит очередь: догоняет не больше двух периодов.
- **Такты сессий независимы.** Планировщик только запускает такт (`onTimer`), тело такта идёт на виртуальном потоке; пока предыдущий такт сессии не кончился, следующий пропускается; одновременных тактов не больше `lab.session.max-concurrent-ticks` (8); такт держит соединение пула, поэтому `spring.datasource.hikari.maximum-pool-size` = 20 (такты + запас для HTTP, при изменении держать больше `max-concurrent-ticks` минимум на 10). Таймер привязан к экземпляру `Running`: снимает и ставит его только код, знающий этот экземпляр, снятие — после коммита (`afterCommit`), поэтому запоздавшее снятие не трогает таймер следующего `play`. Если БД и таймер разошлись, такт под блокировкой перечитывает `playing` и снимает лишний таймер сам; `play` при `playing = true` без таймера перезапускает его.
- **Состояние плеера** — `sessions.player_state`: играет ли, скорость, `total_steps` шкалы, день и номер свечи в дне на шаге курсора (`cursor_*`, верны, пока `cursor_step = current_step`). `pause`, `speed` и `play` не зовут воркера, кроме самой первой команды сессии (число шагов шкалы; день на шаге 0 — первая свеча первого дня, иначе берётся у воркера один раз и запоминается); воркер нужен `step` и тактам. Таймеры только в памяти: при старте (`ApplicationReadyEvent`) все идущие сессии ставятся на паузу (`paused: restart`), призрачных таймеров нет.
- **Пачка шагов.** За такт может пройти несколько свечей (×10, ×100): воркеру уходит один `ReplaySession` без истории с `events_from_step = курсор до пачки` (интервал событий ядра `(events_from_step; up_to_step]`, левая граница не входит) (`SimulationWorkerClient.replaySteps`), событие `step` одно на такт и содержит свечи всех шагов пачки (`bars` — массив на бумагу), исполнения и заявки пачки, портфель и `paperStats` на курсоре (статистика — по бумагам со свечой в пачке). День и номер свечи в дне считаются по барам событий, продолжая с позиции перед пачкой. Событие не опережает курсор (INV-1).
- **Паузы.** Без подписчиков SSE дольше `lab.session.disconnect-pause-after` (5 с) — пауза (`paused: disconnect`); проверяет сам такт по числу подписчиков, точность — период такта (до секунды на ×1); сбой воркера или любая ошибка такта — пауза (`worker_failure`: причина обобщённая, различие — в логе); команда `pause` — `user`; рестарт — `restart`. Любая пауза в потоке — пара событий: `player` (`playing: false`), затем `paused` с причиной; пауза при завершении сессии — только `player`, затем `finished`. Обрыв клиента без закрытия соединения замечает пульс потока (`lab.session.heartbeat`, 2 с, комментарий `:keepalive`).
- **Конец.** Воркер вернул `FINISHED_END` (последний шаг шкалы) → `completed`, `BANKRUPT` → `bankrupt` (курсор останавливается на шаге банкротства), `finish` пользователя → `finished_early`. Завершение пишет статус, останавливает игру, публикует `step` (последний), `player`, `finished` и Spring-событие `SessionFinished` (его слушает модуль отчёта). Повторный `finish` — 200 с тем же итогом; воркер недоступен — 503, сессия остаётся активной. Раскрытие слепой сессии — следствие статуса: `SessionRecord.revealed()` (неслепая либо завершённая); отчёт, история и воспроизведение отдают реальные даты и тикеры только при `true`. Итог `finish` слепой сессии остаётся слепым (`BlindFinishResult`).
- **События** (`SessionEvents`, `sessions.session_event`): тело строит `BlindMasking` (слепая сессия — только маскированные виды, INV-7) по шагам не дальше курсора (INV-1) и пишется в транзакции команды под блокировкой сессии, поэтому номера возрастают в порядке фиксации. Подписчику события отдаются из таблицы по порядку номеров: догон по `Last-Event-ID` и живая доставка — один путь; начальный номер подписки выставляется до регистрации, поэтому новый клиент не получает историю. Без `Last-Event-ID` — только новые; номер из будущего считается последним; не число — 400. Код (`Problem.code`) есть у каждой ошибки и обязателен в контракте; стандартные ошибки Spring получают его по статусу (`ProblemCodes`), фильтры безопасности и `ApiExceptionHandler` ставят свой. Коды ошибок — только через enum `api.ErrorCode`, он же `ProblemCode` в контракте (сверяет `ErrorCodeContractTest`); новый код — в оба места. Типы: `step`, `order_updated` (после принятой команды заявки), `player`, `paused`, `finished`, `report_ready` (публикует модуль отчёта через `SessionEvents.reportReady(sessionId)`).
- **Медленный клиент.** Отправка подписчику — одна активная на подписку, на виртуальном потоке (не больше `lab.session.max-concurrent-sends`); уведомления во время отправки схлопываются. Пульс ничего не ждёт; отправка, не завершившаяся за `2 * heartbeat`, обрывает подписку (клиент переподключается с `Last-Event-ID`); `Sink.abort` вызывается на отдельном потоке, потому что `SseEmitter` берёт ту же блокировку записи, что и зависшая отправка.
- **Хранение событий.** События завершённой сессии старше `lab.session.event-retention` (24 ч) удаляет `SessionEvents.cleanup` (раз в час); триггер БД разрешает удаление только у завершённой сессии, `UPDATE` запрещён. Журнал команд (INV-8) остаётся источником состояния.
- **Ошибки.** 409 `PLAYER_STATE_CONFLICT` (`step` во время play, play и step на последнем шаге — защита: пройдя последний шаг, сессия завершается и дальше идёт `SESSION_NOT_ACTIVE`), 409 `SESSION_NOT_ACTIVE` (сессия завершена), 400 (неизвестное действие, скорость вне 1/5/10/100, скорость у play/pause/step), `Idempotency-Key` — как в арене (`CommandRunner`, общий путь с заявками).
- **Снимок и такт.** `GET /sessions/{id}` читает сессию и журнал без общей транзакции с тактом: снимок может отстать на такт. Записи журнала читаются не дальше курсора прочитанной сессии (`ArenaJournal.records`): ядро отвергает записи дальше `up_to_step`, а курсор мог уйти вперёд между чтением сессии и журнала.
- Тесты: `PlayerApiTest` (PostgreSQL, MockMvc, `FakeWorker` и `ManualTimer`): такты на каждой скорости, пауза/шаг/скорость, 409, автопауза без подписчиков, сбой воркера, перезапуск, `Last-Event-ID`, INV-1 (`noEventCarriesDataBeyondTheCursor`), INV-7 (`blindEventsCarryNoTickersDatesOrRubles`), завершение, раскрытие, пачка шагов без истории, медленный клиент, независимость тактов, согласованность таймера и БД, очистка событий.

## gRPC-контракт (proto)
`proto/simulation.proto` и `proto/common.proto` — копии `core/proto/` с ветки `main` репозитория `core` (источник правды), без изменений. Java-код (protobuf и gRPC-стабы, пакет `pac.simulation.v1`) генерируется при сборке плагином `com.google.protobuf` в `build/generated` и не коммитится; ErrorProne и Spotless его не проверяют. Джоба CI `proto-sync` падает, если копия отличается от `core/main`. Контракт изменился в `core` — PR в `backend` с новой копией сразу после слияния PR в `core` (порядок контракта — `home/AGENTS.md`).

Набор `src/e2eTest/java` (пакет `ru.tinvest.trainer.e2e`) поднимает полное приложение на случайном порту и ходит в него по HTTP, как браузер. ```bash

```bash
./gradlew e2eTest --no-daemon                         # весь набор (около 1-2 минут при готовом образе)
./gradlew e2eTest --tests '*MoneyReconciliation*'     # только сверка денег
```

Что проверяют (INV-6, INV-7, INV-8): `BlindScenarioE2eTest` — вход, слепая сессия, снимок, заявки (в том числе отказ и отмена), шаги плеера, обрыв SSE и догон по `Last-Event-ID`, F5, завершение, раскрытие периода, отчёт, история, воспроизведение; `LeakScanner` рекурсивно обходит **каждый** ответ слепой сессии до завершения (тикеры, названия, даты и время, цены архива, капитал, поля рублей) и на неслепой сессии находит всё (положительный контроль); `blindMaskNeverLetsPaperFieldsThrough` — то же для слепых сессий всех категорий и числа бумаг со случайными командами и отказами. `MoneyReconciliationE2eTest` — случайные рыночные сделки (зерно `20261120`) идут через API, `MoneyModel` независимо считает цену исполнения, сумму, комиссию и сбор, остаток денег и стоимость портфеля в `BigDecimal` по правилам `decisions.md`; сверка до копейки после каждого шага, затем издержки отчёта по видам, итоговый капитал и воспроизведение журнала. ## Окружение
Локальный стек в `deploy/`: `caddy` (HTTPS, единственный с опубликованными портами 80/443, INV-10) → `backend`; внутри сети `postgres` (17), `clickhouse` (25.8) и `worker` (образ `simulation-worker`, собирается из `../core` по его `Dockerfile`).
Соседние репозитории лежат рядом с `backend` (`../core`, `../frontend`); нет локально — `home/scripts/clone-repos.sh`.

```bash
cp deploy/.env.example deploy/.env      # задать POSTGRES_PASSWORD и CLICKHOUSE_PASSWORD
# Образы собираем напрямую: `compose build` через bake требует --allow=fs.read=.. для ../../core
docker build -t simulation-worker ../core          # или путь к core; тяжёлая сборка C++
docker build -f deploy/backend.Dockerfile -t trainer-backend .
docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d --no-build
curl -k https://localhost/api/health    # 200 (-k: сертификат внутреннего CA Caddy)
docker compose -f deploy/docker-compose.yml --env-file deploy/.env ps   # порты только у caddy
docker compose -f deploy/docker-compose.yml --env-file deploy/.env down -v
```

Подсеть `internal` закреплена: `172.28.0.0/24`. Если `up` падает с `Pool overlaps with other one on this address space`, смени подсеть в `deploy/docker-compose.yml` и `server.tomcat.remoteip.internal-proxies` в `application.yml` (тест проверяет, что они совпадают). Если хост принимает IPv6 на 443, а `edge` без IPv6, docker-proxy показывает Caddy адрес шлюза и IPv6-клиенты делят один IP в лимите входа — проверить при развёртывании.

`CORE_DIR` в `deploy/.env` — путь к репозиторию core для `up --build` (по умолчанию `../../core` от `deploy/`; в worktree задать явно).

Frontend: `FRONTEND_DIST` в `deploy/.env` — каталог сборки (`../../frontend/dist/<имя>/browser`); не задан — Caddy отдаёт заглушку `deploy/frontend-stub`. Сборка образа worker тяжёлая (C++, gRPC).
